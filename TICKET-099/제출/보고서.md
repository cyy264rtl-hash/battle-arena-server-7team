### A3. 패킷이 두 조각으로 나눠 오면 본문을 덜 읽는다

- **재현 방법**
  1. OutsourcedServer 실행
  2. LoadTester → 2번 (55바이트 본문을 27 + 28로 나눠 50ms 간격으로 전송)
  3. 서버 콘솔과 LoadTester가 받은 채팅을 본다
- **증거** : 화면 `증거/A_전_2번_서버.png`, `증거/A_전_2번_LT.png` → `증거/A_후_2번_서버.png`, `증거/A_후_2번_LT.png` / 로그 `증거/로그/A_전_2번_서버로그.txt`, `증거/로그/A_전_2번_LoadTester로그.txt` / 고친 뒤 `증거/로그/A_후_2번_서버로그.txt`, `증거/로그/A_후_2번_LoadTester로그.txt`
- **원인** : `OutsourcedServer/PacketHelper.cs` 51줄, 63줄. ReceiveAsync를 한 번만 부르고 실제로 몇 바이트를 받았는지 확인하지 않는다.
  TCP는 경계를 보장하지 않아서 보낸 대로 한 번에 오지 않는다(3주차 길이 헤더를 붙인 이유와 같다). 앞 조각 27바이트만 읽은 채로 55바이트짜리 버퍼를 JSON으로 파싱해서, 서버 로그에 `JsonReaderException: Unterminated string ... position 55` 가 찍혔다. 이 예외가 A2의 async void를 타고 올라가서 서버까지 꺼졌다.
  5주차 PacketHelper에는 원하는 바이트 수를 다 받을 때까지 반복하는 `ReceiveExactAsync`가 있었는데 납품본에서 빠져 있다.
- **고친 코드**

```csharp
// before (51줄, 63줄 : 한 번만 읽음)
int n = await socket.ReceiveAsync(new ArraySegment<byte>(header, 0, 4), SocketFlags.None);
await socket.ReceiveAsync(new ArraySegment<byte>(body, 0, bodyLength), SocketFlags.None);

// after (다 받을 때까지 반복)
byte[]? header = await ReceiveExactAsync(socket, 4);
byte[]? body   = await ReceiveExactAsync(socket, bodyLength);

private static async Task<byte[]?> ReceiveExactAsync(Socket socket, int count)
{
    byte[] buffer = new byte[count];
    int received = 0;
    while (received < count)
    {
        int n = await socket.ReceiveAsync(
            new ArraySegment<byte>(buffer, received, count - received), SocketFlags.None);
        if (n == 0) return null;
        received += n;
    }
    return buffer;
}
```

- **결과** : 고친 뒤(A2, A3 둘 다 적용) 서버가 안 꺼지고, 나눠 보낸 채팅 `AAAA-분할전송-테스트-BBBB` 와 그다음 `정상패킷-그다음` 이 둘 다 돌아왔다.

```csharp
// after

```

### A5. UDP 위치 값에 이전 패킷 글자가 붙어서 엉뚱한 좌표가 된다

- **재현 방법**
  1. OutsourcedServer 실행
  2. LoadTester → 6번 (접속 → MOVE 10개 → 종료를 5회 반복. y는 1~10만 보낸다)
  3. LoadTester가 받은 STATE의 좌표를 본다
- **증거** : 화면 `증거/A_전_6번_서버.png`, `증거/A_전_6번_LT.png` → `증거/A_후_6번_서버.png`, `증거/A_후_6번_LT.png` / 로그 `증거/로그/A_전_6번_LoadTester로그.txt`, `증거/로그/A_전_6번_서버로그.txt` / 고친 뒤 `증거/로그/A_후_6번_LoadTester로그.txt`, `증거/로그/A_후_6번_서버로그.txt`
- **원인** : `OutsourcedServer/UdpServer.cs` 80줄 `Encoding.UTF8.GetString(buffer)`. 받은 길이(`result.ReceivedBytes`)가 아니라 1024바이트 버퍼 전체를 문자열로 바꾼다.
  고치기 전 STATE가 `STATE|2,ReBot2,6,110`, `STATE|3,ReBot3,9,210` 처럼 나왔다. y는 1~10만 보냈으니 110, 210은 나올 수 없는 값이다. 직전에 받은 `MOVE|1|10|3|10`(14글자) 위에 `MOVE|2|1|6|1`(12글자)이 덮어써지면 뒤 2글자 `10`이 남아서 `MOVE|2|1|6|110` 으로 읽힌다. 버퍼 나머지는 `\0`이라 int.TryParse가 그대로 통과시키는 것으로 보인다. 5주차 PositionSync는 `GetString(buffer, 0, r.ReceivedBytes)` 였다.
  회차마다 결과가 달랐던 이유도 이것이다. 직전 패킷이 얼마나 길었는지에 따라 붙는 글자가 달라진다.
- **고친 코드**

```csharp
// before
string msg = Encoding.UTF8.GetString(buffer);
// after
string msg = Encoding.UTF8.GetString(buffer, 0, result.ReceivedBytes);
```

- **결과** : 고친 뒤 STATE가 `6,1`, `9,1`, `12,2`, `15,1` 처럼 보낸 범위(1~10) 안의 값으로 나온다.

### A6. 다른 사람의 PlayerId를 적어 보내면 그 사람 위치가 바뀐다

- **재현 방법**
  1. OutsourcedServer 새로 실행
  2. LoadTester → 7번 (A, B 접속 → B가 자기 소켓으로 `MOVE|A의ID|9999|30|15` 전송)
  3. LoadTester 문구만 보지 말고 서버 통계의 UDP적용 / 버림을 같이 본다
- **증거** : 화면 `증거/A_전_7번_서버.png`, `증거/A_전_7번_LT.png` → `증거/A_후_7번_서버.png`, `증거/A_후_7번_LT.png` / 로그 `증거/로그/A_전_7번_서버로그.txt`, `증거/로그/A_전_7번_LoadTester로그.txt` / 고친 뒤 `증거/로그/A_후_7번_서버로그.txt`, `증거/로그/A_후_7번_LoadTester로그.txt`
- **원인** : `OutsourcedServer/UdpServer.cs` 120~124줄. 첫 패킷일 때 주소를 등록만 하고, 그 뒤로는 보낸 주소가 등록된 주소와 같은지 확인하지 않는다. UDP는 접속 개념이 없어서 패킷 안의 PlayerId만 믿으면 누구든 남의 캐릭터를 움직일 수 있다.
  LoadTester는 "A의 위치가 (5,5)에서 안 바뀌었습니다"라고 떠서 처음엔 정상인 줄 알았다. 그런데 서버 통계가 `UDP적용 3 | 버림 0` 이었다. A 1개, B 1개, 그리고 B가 A 이름으로 보낸 것까지 3개가 적용된 것이다. LoadTester는 A의 소켓에 먼저 쌓여 있던 예전 STATE 하나만 읽어서 (5,5)가 나온 것으로 판단했다.
- **고친 코드**

```csharp
// before
if (session.UdpEndPoint == null)
{
    session.UdpEndPoint = from;
    ...
}

// after
if (session.UdpEndPoint == null)
{
    session.UdpEndPoint = from;
    ...
}
else if (!session.UdpEndPoint.Equals(from))
{
    // 등록된 주소가 아닌 곳에서 남의 PlayerId로 보낸 패킷은 버립니다.

    return;

```

- **결과** : 고친 뒤 `UDP적용 2 | 버림 1`. B가 A 이름으로 보낸 패킷이 버려졌다.

### 서버 쪽에서 본 것

서버만 새로 켜고 50명 한 번만 다시 돌리면서 서버 통계 줄을 봤다. 켜자마자 스레드는 3개였다(`증거/B1_서버시작직후.png`). (CSV 7행, `증거/B1_재측정50명_LoadTester.png`, `증거/B1_고치기전_통계.png`, `증거/로그/B1_고치기전_서버로그.txt`)

```
t=135s | 접속  0 | 스레드  3 | 가용워커 32765
t=138s | 접속 14 | 스레드 15 | 가용워커 32752
t=141s | 접속 18 | 스레드 19 | 가용워커 32748
t=143s | 접속 22 | 스레드 23 | 가용워커 32744
t=146s | 접속 26 | 스레드 27 | 가용워커 32740
(LoadTester가 끊음, 에러 27줄)
t=148s | 접속  0 | 스레드 27
t=168s | 접속  0 | 스레드  3
```

여기서 본 것은 세 가지다.

1. 스레드 수가 매번 접속 수 + 1이다. 접속한 사람 한 명이 스레드 하나를 계속 들고 있다.
2. 50명이 한꺼번에 왔는데 접속은 2~3초에 4명씩밖에 안 늘었다. 처음 14명 정도는 바로 받았고 그 뒤로는 스레드가 늘어나는 속도에 맞춰서만 들어왔다.
3. 26~27명쯤에서 LoadTester의 대기 시간이 끝나 전부 끊겼다. 이번 측정의 성공 수가 27인데 서버 최대 접속도 26~27이라 숫자가 맞는다.

가용워커는 32,740 아래로 내려가지 않았다. 공지에 "0이면 뭔가 잘못된 것"이라고 되어 있어서 처음엔 가용워커만 봤는데, 이 PC는 최대치가 32,767이라 0까지 갈 일이 없었다. 문제는 스레드가 모자란 게 아니라 늘어나는 속도가 느린 쪽이었다.

### 왜 거기서 나빠지나

원인 코드는 `OutsourcedServer/PacketHelper.cs` 51줄과 63줄이다.

```csharp
int n = await Task.Run(() => socket.Receive(header, 0, 4, SocketFlags.None));   // 51줄
await Task.Run(() => socket.Receive(body, 0, bodyLength, SocketFlags.None));    // 63줄
```

주석에는 "Receive는 블로킹 함수라서 Task.Run으로 감싸 비동기화했습니다"라고 써 있다. 그런데 4주차 수업 자료에 그대로 나온 "흔한 실수"가 이거다. Task.Run은 스레드풀에서 스레드를 하나 빌려 오는 거고, 그 스레드 안에서 `socket.Receive`가 데이터가 올 때까지 멈춰 있는다. 겉모양만 await이고 실제로는 접속한 사람 수만큼 스레드가 Receive에 묶여 있는 구조다.

공지문 질문 순서대로 답하면 이렇다.

- **접속자 한 명이 서버 자원을 어떻게 잡아먹나** : `ClientSession.RunAsync()`가 `ReceiveAsync`를 부르고, 그 안의 Task.Run이 스레드 하나를 가져가서 클라이언트가 패킷을 보낼 때까지 `socket.Receive`에서 놓지 않는다. 접속이 끊길 때까지 계속 반복되니까 한 명 = 스레드 한 개다. 통계의 "스레드 = 접속 + 1"이 이걸 보여준다.
- **왜 어느 숫자를 넘으면 갑자기 느려지나** : 스레드풀은 처음에 최소 워커 수(이 PC는 12)까지는 바로 내준다. 10명은 이 안에 들어가서 다 같이 처리됐다. 그 이상은 스레드풀이 새 스레드를 천천히 하나씩 늘려서 주는데, 로그로 보면 2~3초에 4개 정도였다. 50명이면 뒤쪽 사람은 자기 차례가 오기 전에 9초가 지나버린다.
- **스레드가 모자라면 어떻게 되나** : 새로 온 사람의 로그인 처리가 스레드를 못 받아서 줄을 선다. 서버는 죽지 않고 에러도 안 나는데, 클라이언트 쪽에서 보면 그냥 응답이 없다. 결국 클라이언트가 포기하고 끊으면서 서버에 강제 종료 에러가 한꺼번에 찍혔다.
- **기다리는 동안 스레드가 필요한가** : 필요 없다. 4주차 때 "기다리는 동안 쓰레드를 놀리지 말자", "네트워크 대기 중에는 CPU가 할 일이 없다"고 배웠다. 네트워크 대기는 `socket.ReceiveAsync`처럼 OS에 맡기고 await하면 데이터가 올 때까지 스레드를 반납한다.

측정이 끝나고 접속이 0이 됐는데도 스레드 27개가 20초 정도 그대로 남아 있다가 t=168s에 3개로 줄었다. 늘어난 스레드를 스레드풀이 바로 버리지 않고 한동안 들고 있는 것 같다. 첫 측정 후에 접속 0인데 스레드가 55개였던 것도 같은 이유로 보인다.
